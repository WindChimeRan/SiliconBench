## Fixes Applied

### sglang (chat + agent) — `6dd6027`
- **Error**: `ValueError: 'qwen3_asr' is already used by a Transformers config`, from
  `configs/qwen3_asr.py:167 AutoConfig.register(...)` during the
  `server_args -> configs/__init__` import chain. Server never bound its port
  ("failed to start within 300 seconds").
- **Diagnosis**: `install_sglang.sh:42` runs `uv pip install --upgrade mlx mlx-lm`
  *after* the editable install; resolving mlx-lm's deps upgraded transformers
  5.12.1 → 5.15.0, past the `transformers==5.12.1` pin in sglang's own
  `python/pyproject.toml:64`. transformers 5.15.0 ships a **native** qwen3_asr model
  (`transformers/models/qwen3_asr/`, registered via `models/auto/auto_mappings.py` —
  not `configuration_auto.py`), so sglang's own registration collides.
- **Fix**: re-pin transformers after the mlx upgrade, reading the version from
  pyproject so it rolls forward when upstream bumps it.
- **Verification**: 5.12.1 confirmed to lack any `qwen3_asr` module; the exact failing
  import now succeeds; and the **full backfilled benchmark passed 100/100 requests at
  all three concurrency levels** (TTFT 65–298 ms, 106–147 tok/s).

## ⚠ Agent-split measurement artifact — read before interpreting mlx_lm

**The agent split penalizes frameworks that implement structured tool-call parsing.**
`benchmark.py` counts any response with ≤1 generated token as a silent failure. Agent
prompts (BFCL V3 / Hermes) frequently elicit a tool call as the correct next turn.

Verified from the `*_outputs.jsonl` sidecars — prompt `a000_vlong_bfcl_v3`, agent, c=1,
identical model and prompt:

| Framework | tokens | `content` |
|---|---|---|
| llamacpp | 18 | `<tool_call>{"name": "GorillaFileSystem.rm", ...}</tool_call>` (raw text) |
| vllm_metal | 18 | identical raw text |
| omlx | 2 | identical raw text |
| vllm_mlx | 11 | `[Calling tool: GorillaFileSystem.rm({})]` |
| mistralrs | 255 | `''` |
| ollama | 254 | `''` |
| **mlx_lm** | — | **no record — this prompt is one of its 30 "failures"** |

mlx_lm's `error_samples` name this exact prompt with `finish_reason=tool_calls` and 0
tokens: it parses the tool call into a structured field, leaving `content` empty.
llamacpp and vllm_metal score 0 failures precisely because they **don't** parse tool
calls and pass raw text through.

**mlx_lm's 30/100 agent failures at c=1 and c=8 are therefore not real failures.**
Comparing `failed` counts across frameworks on the agent split compares tool-call
serialization strategy, not reliability. Not fixed: the heuristic is in
`benchmark.py`, which is framework-agnostic and load-bearing.

Check `finish_reason` before concluding:
- `tool_calls`, 0 tokens → **artifact** (mlx_lm)
- `error`, 0 tokens → **real server error** (vllm_mlx at c=8/16)
- `None`, 0 tokens → **real silent failure** (mistralrs at c=8/16)

## Suspicious Successes

**Token-divergence warning fires across frameworks.** e.g. llamacpp
`30/100 requests had server completion_tokens diverging >5% from SSE chunk count
(avg ratio 1.18x)`; mlx_lm 32/100 @1.23x; sglang 30/100 @1.19x. Per-request
`throughput_avg_tps` and `itl_avg_ms` are chunk-based and therefore **suspect** for
affected frameworks; aggregate token counts (server `completion_tokens`) and TTFT are
unaffected. This is widespread, not framework-specific — treat cross-framework ITL
comparisons in this run with caution.
