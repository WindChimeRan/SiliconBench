## Cap Hits

`⚠ hf_transformers exceeded 3600s wall time — killing`. **This is precisely the case
the cap exists for** — `run_all_apple.sh:124` notes hf_transformers on the agent split

## Skipped Cells

### mistralrs — chat + agent — text-only `gemma4` unsupported
- **Error**: ``GGUF architecture `gemma4` is supported only as a multimodal model. Pass
  its companion projector with `--mmproj <file>` ... text-only `gemma4` checkpoints are
  not supported``
- **Why skipped — a deliberate policy call, not a gap**: `models/gemma-4-e4b-it.sh`
  documents *"we benchmark text-only ... `mmproj-*.gguf` files in the unsloth repo are
  not fetched."* Passing `--mmproj` would make mistralrs the only framework loading
  vision/audio projectors, so its numbers would no longer be comparable to the others.
  Honoring the repo's stated text-only policy and leaving a clean gap is correct.
  Reversing that policy is the user's call.

### sglang — chat + agent — multimodal checkpoint vs. text-only MLX loader
- **Error**: `ValueError: Received 54 parameters not in model:
  language_model.model.layers.{24..27}.self_attn.{k_norm,k_proj,v_proj}.weight, ...`
  from `mlx/nn/layers/base.py:185` via `mlx_lm/utils.py:415 load_model` ←
  `hardware_backend/mlx/model_runner.py:513 mlx_lm_load`. Died during
  `Scheduler.__init__ -> init_tp_model_worker`; the `Killed: 9` is sglang's own
  `kill_process_tree`, **not** jetsam.
- **Diagnosis**: this is the *already-documented* limitation in
  `models/gemma-4-e4b-it.sh` — the Gemma-4 MLX port is a multimodal mlx-vlm package
  with `vision_tower` / `audio_tower` / `language_model.*` keys that **mlx_lm's
  text-only loader rejects**. The profile works around it for the `mlx_lm` slot via
  `export MLX_BACKEND="mlx_vlm"` (which is why mlx_lm succeeds here), but sglang's MLX
  backend calls `mlx_lm_load` internally and exposes no equivalent knob.
- **Why skipped**: fixing it means editing `.frameworks/sglang/` (off-limits) or
  reimplementing mlx_vlm routing inside sglang's model runner — framework work, not
  adapter work.

### omlx — chat + agent — served the WRONG MODEL
- **Error**: HTTP `409 Conflict` on all 300 requests per split:
  `Model 'RedHatAI--Qwen3-8B-speculator.dflash' is unavailable after a previous load
  failure: Couldn't instantiate the backend tokenizer`.
- **Diagnosis**: omlx is a multi-model server and `run_all` uses `/v1/models data[0]`
  as the API `model` field. `serve_omlx.sh:17-22` resets `--model-dir` to a *single*
  symlink precisely to keep that unambiguous — and the symlink was correct
  (`gemma-4-e4b-it-bf16-mlx` → the MLX dir). But omlx also discovers models from
  outside `--model-dir`, and `data[0]` resolved to an unrelated
  `RedHatAI--Qwen3-8B-speculator.dflash`.
- **This is the most dangerous failure mode in the sweep**: it produced a *complete
  result file* for a model that was never actually served. Only cross-checking the
  `model` field inside each result JSON revealed it — file presence and even
  per-request success/failure counts would not have.
- The affected result files were removed in `9cbd277`; the omlx cells for
  Qwen3-0.6B and Qwen3.5-0.8B were checked and **do** report the correct model.
- **Not fixed**: constraining omlx's discovery beyond `--model-dir` needs investigation
  of omlx's own model-registry behaviour, and `run_all_apple.sh`'s `data[0]` selection
  is off-limits to edit.

### ollama — chat + agent — no Ollama registry tag
Same root cause as Qwen3.5-0.8B: `models/gemma-4-e4b-it.sh` notes ollama is *"not in
the 'fast engines' chorus for this model"*, `config.sh:43` derives a fallback tag that
doesn't exist, and every request 404s. Guarded by `9916334`; bogus results removed in
`9cbd277`. See the Qwen3.5-0.8B journal for the full write-up.

## Degraded Cells

Real server-side errors (`finish_reason=error`), consistent with its concurrency

### mlx_lm (6%) / vllm_metal (7%) — agent
Low failure rates. Note the agent-split tool-call artifact documented in the
Qwen3-0.6B journal before reading these as reliability differences — frameworks that
parse tool calls into structured fields are penalized by the ≤1-token silent-failure
heuristic.
